# Tunables

Defaults are calibrated against real incidents (see the [CHANGELOG](../CHANGELOG.md)); the one change since v6.1 is the release floor, `1.0` since 6.5.0 (`RESV_FLOOR`). **Override only with evidence.**

## Where settings go

**Not on the container.** On the Dispatcharr image, `RESV_*` variables set on the container (Docker `environment:`, an Unraid Variable) never reach reservoarr: Dispatcharr starts its workers through `su -`, which clears the environment, and re-exports only its own list of variables. Setting them there changes nothing.

Put them in the stream profile, in front of the script, with `/usr/bin/env`:

| Field | Value |
|---|---|
| Command | `/usr/bin/env` |
| Parameters | `RESV_TARGET_S=40 RESV_AUDIO_LANG=fra /data/reservoarr/reservoarr.py {streamUrl} {userAgent}` |

- Any number of `RESV_X=value` pairs, space-separated, before the script path. Values must not contain spaces.
- Create a **new** profile (Settings → Stream Settings → Profiles) rather than editing the generated one: **Generate Stream Profile** resets the command and parameters of a profile with the same name.
- The profile lives in Dispatcharr's database, so it survives plugin updates and container recreation. It takes effect on the next tune; no restart.
- A profile per setting combination also gives you per-channel values (assign it to those channels), which `RESV_TS_CHANNEL` needs anyway.
- Without `/usr/bin/env` and without a variable, the script runs on its defaults.

## Variables

| Env var | Default | What it does |
|---|---|---|
| `RESV_PREFILL_BYTES` | `1572864` (1.5 MB) | Sniff target before releasing to ffmpeg. **NOT** a reservoir fill — Plex's tuner times out around 15s, so a full prefill caused "won't start, then loads on retry". |
| `RESV_PREFILL_MAX_S` | `3.0` | Sniff timeout. Must stay well under Dispatcharr's `CONNECTION_TIMEOUT` (~10s). |
| `RESV_HEADSTART_S` | `5.0` | Seconds of content released unpaced after prefill. Gives Plex its startup buffer fast; the rest of the CDN's front-load burst stays banked. |
| `RESV_TARGET_S` | `30.0` | Cushion level the controller holds. Tune higher only if your CDN's worst gaps are longer. |
| `RESV_GRACE_S` | `45.0` | Only with `RESV_FLOOR` under `1.0`: the first N seconds still release at no less than realtime, then the floor drops to `RESV_FLOOR`. Keeps a sub-realtime feed from draining the player while it holds only the headstart. Before 6.5.0 the floor after it was a fixed `0.97`, and `RESV_GRACE_S=inf` keeps `1.0` on those releases. |
| `RESV_FLOOR` | `1.0` | Lowest release rate, as a multiple of the content rate, while the cushion is under `RESV_TARGET_S`. `1.0` never feeds the player below realtime: the cushion holds what the CDN front-loads (minus `RESV_HEADSTART_S`) and what its catch-up bursts bring, up to the target, and does not grow past that on its own. Under `1.0` the reservoir also banks by feeding the player slower than realtime, and every second banked comes out of the player's own buffer: at `0.97` the player gets 0.97s of content per second, so a client with a small live buffer (Channels, TiviMate) runs dry and stutters until the cushion reaches the target, while the log looks healthy and `out` sits ~3% under `crate` ([discussion #46](https://github.com/brko7/reservoarr/discussions/46)). Set `0.97`, the fixed value before 6.5.0, only behind a tuner that dies on input silence (Plex Live TV) whose client buffers deeply enough to absorb it, on a CDN that leaves the cushion well under the target. A decimal above 0 and at most 1; anything else is logged and read as `1.0`. Values under `0.7` act as `0.7`, the lowest the controller asks for (an empty cushion) (6.5.0). |
| `RESV_MAX_BYTES` | `268435456` (256 MB) | Reservoir hard cap. Worst-case RAM per concurrent stream. |
| `RESV_STALL_S` | `25.0` | No-ingest watchdog (#4). If no bytes arrive for this long while running, force a reconnect WITHOUT flushing the buffer. A silent connection is cut at once (6.4.0; a hang while connecting still waits out the 30s timeout; before, the reconnect waited out the 30s socket timeout, so values under 30 changed nothing). A full reservoir is not a stall. `0` disables. |
| `RESV_DRY_EXIT_S` | `5.0` | The process exits when it has delivered data, the reservoir is empty and no byte has arrived for this long, so Dispatcharr retries or fails over at once instead of finding out through its health monitor 20-25s later (6.7.0). A channel of under ~308 kbps gets twice its read time instead, since two of its reads take longer than this. While the reservoir is empty and this time has not passed, a failed connection is retried every second instead of backing off. A process that has delivered nothing never exits this way: it stays to wait for its first byte (`RESV_GIVEUP_TRIES` is that path). Dispatcharr counts each exit as a failed attempt, and three with no other stream to try end the channel; only a switch or 30 minutes without a failure clears the count. So a URL gets one such exit every 31 minutes, kept as an empty `dryexit-<hash>` file in `RESV_LOG_DIR` (one per URL, nothing rotates them; the hash keeps the URL's credentials out of the name). A later outage in that time rides it out as before, and Dispatcharr's health monitor acts on it after 20-25s. If the file cannot be written, the process stays too. `0` never exits this way, as before 6.7.0. |
| `RESV_GIVEUP_TRIES` | `0` | Upstream attempts that may end without a single byte before the process exits, so Dispatcharr counts a failed attempt and, after its own retries, moves the channel to the next stream. Errors and connects that close empty both count; once any byte has arrived it never fires. `0` retries forever, as before. Without it, a stream the edge answers `403` keeps the channel "connecting" until the client gives up, and the chain is never walked. A refused attempt ends the process within the second, without waiting out `RESV_PREFILL_MAX_S` (6.3.7). |
| `RESV_REJECT_MP4` | `0` | `1` checks the first chunk of every upstream connection once: an `ftyp` box at offset 4, on a chunk that does not start with the TS sync byte, means the edge sent a finished MP4 file (a provider's "channel off the air" clip) instead of a live TS; the `Content-Type` is ignored, since CDNs label live TS as `video/mp4` too. The bytes are dropped, the connection closed and the connection counts as an attempt without data, so with `RESV_GIVEUP_TRIES` set the process ends as it does on a `403` instead of feeding the file to ffmpeg, which fails on it after ~10s per Dispatcharr attempt. `0` feeds every answer to ffmpeg, as before (6.3.8). Independent of this tunable, since 6.3.9 an HLS playlist (`#EXTM3U`), HTML page or XML document in the first chunk is always rejected the same way: it can never be a live TS. |
| `RESV_AUDIO_CODEC` | `ac3` | Codec the audio is re-encoded to. `ac3` is `-c:a ac3 -b:a 192k -ac 2`, the encode Plex needs (invariant #3). `aac` is `-c:a aac -b:a 192k -ac 2 -ar 48000`, for servers whose clients do not take AC3 (Jellyfin then converts the AC3 back to AAC on every such stream) or send it undecoded to a soundbar: a player with audio passthrough on cannot absorb a jump in the audio timeline, while AAC is always decoded. Any other value, `copy` included, falls back to `ac3` and logs one line at startup (an empty value stays silent): the audio is never copied. Behind Jellyfin, switching takes effect on clients only after Jellyfin re-probes: it caches the probe of each live channel in its `/cache/mediainfo` and keeps announcing AC3 until those files are removed (6.3.11). |
| `RESV_AUDIO_FILL_GAPS` | `0` | `1` adds `-af aresample=async=1` with either codec: a hole in the audio timeline longer than 0.1s is filled with silence and an overlap is trimmed, so the output audio stays continuous where the source drops packets. Jumps beyond ffmpeg's `dts_delta_threshold` (10s) are handled as discontinuities on the `mpegts` input before the filter, so far timestamps are not turned into minutes of silence, and audio that stops altogether does not hold the video (6.3.11). |
| `RESV_REPLAY_SKIP` | `0` | `1` drops what an edge resends after a plain reconnect: the fetcher remembers the last PCR taken before the seam and discards packets of the new connection until the PCR passes it, so the same seconds are not played twice and the replay is not banked as new cushion. The new connection's packets are held until the seam is confirmed, so a seam it gives up on passes through whole, as before: a replay that starts further back than `RESV_REPLAY_MAX_S`, carries a discontinuity flag, jumps back or more than 10s forward, shows no advancing PCR within 1 MB (a repeated PCR is a legal duplicate), or ends with the connection before the seam. The held replay counts against `RESV_MAX_BYTES` together with the reservoir, and the gate also gives up when the reservoir falls below 3s of content while it holds, so a replay arriving at realtime never stalls playback. Never after a flushing reconnect, and a replay still held when a flush is requested is dropped with the reservoir. |
| `RESV_REPLAY_MAX_S` | `60.0` | Longest replay `RESV_REPLAY_SKIP` will drop. A new connection that starts further back than this is treated as a new timeline and passed through. |
| `RESV_TS_CHANNEL` | empty | A channel id; Dispatcharr fills `{channelId}` in the profile parameters, so the profile carries `RESV_TS_CHANNEL={channelId}`. Every process of that channel then continues the output timeline of the one before, instead of starting again at PTS 0: at launch it reads `{RESV_LOG_DIR}/pts-<id>.json`, projects the previous process's last output PTS to now, and hands ffmpeg `-output_ts_offset` one second past it (the wall clock when there is no earlier process). The last PTS is read off ffmpeg's own output, which reservoarr relays to stdout, and written back every 2s and on exit, under an `flock` on `pts-<id>.json.lock`; when two processes overlap in a switch, the later timeline wins. An output PTS more than 30s ahead of where the wall clock puts it is ignored, so a corrupt PES header cannot push the saved timeline hours ahead (the count is logged on exit), and a state file with a non-finite end, or one more than ~13h ahead, falls back to the wall clock. The lock file and, after a crash between write and rename, a `pts-<id>.json.<pid>` stay in `RESV_LOG_DIR`: one lock per channel, nothing rotates them. **It has to be set per channel, in the profile:** a container-wide value would give every channel the same timeline, and the profile the plugin generates (`{streamUrl} {userAgent}`) does not set it. Create a profile with command `/usr/bin/env` and parameters `RESV_TS_CHANNEL={channelId} /data/reservoarr/reservoarr.py {streamUrl} {userAgent}`. Before 6.7.0, without it a stream switch (a failover, a fallback slate, a return from it) sent PTS back by however long the previous process ran, and a downstream `-copyts` transcoder such as Jellyfin's drops every frame until the new timestamps catch up; `RESV_TS_WALLCLOCK` now takes that down to the small step it describes, and this removes the rest. Empty leaves ffmpeg's stdout going straight to Dispatcharr, and `RESV_TS_WALLCLOCK` applies. |
| `RESV_TS_WALLCLOCK` | `1` | With `RESV_TS_CHANNEL` empty, every process starts its output timestamps on the wall clock (`-output_ts_offset`, modulo the 33-bit wrap), so a restart no longer sends PTS back by the length of the session, with no state file and no channel id (6.7.0). After an outage time moves forward. A switch with no gap can still step back, by however far the old process's output ran ahead of the wall clock: the `RESV_HEADSTART_S` head start, and more while the controller has been bleeding a cushion above the target. `RESV_TS_CHANNEL` removes that step too. Timestamps now start anywhere in the 33-bit range, and cross its wrap within 26.5h. `0` starts every process from zero, as before. |
| `RESV_TS_RECONNECT` | `0` | #5 ingest-corruption detector action mode. `0` = log-only ("would-fire"). `1` = arm the forced reconnect+flush. **See arming guidance in [CHANGELOG](../CHANGELOG.md).** |
| `RESV_CC_ERR_PER_WIN` | `3` | #5 trigger: CC errors per 15s window to flag. |
| `RESV_SYNC_ERR_PER_WIN` | `2` | #5 trigger: sync losses per 15s window to flag. |
| `RESV_TS_SUSTAIN_WINS` | `2` | #5: consecutive flagged windows before action. |
| `RESV_LOG_DIR` | `/data/scripts/logs` | Where `delaybuf.log` lives. Set to a writable dir if not running under the AIO container. |
| `RESV_FFMPEG_BIN` | `/usr/local/bin/ffmpeg` | ffmpeg path. Override on dev hosts (`/opt/homebrew/bin/ffmpeg`, `/usr/bin/ffmpeg`). |
| `RESV_AUDIO_LANG` | empty | A 3-letter ISO 639-2 language code (`fra`, `eng`, `deu`), case and surrounding spaces ignored. Adds `-metadata:s:a:0 language=<code>` to the output, so a player lists the audio track as that language instead of "Unknown". Anything else (`fr`, `francais`) is logged as ignored: ffmpeg writes no tag for it. It replaces any language the provider already sends, so it suits a profile for one language. MPEG-TS carries no track title, so a `title=` cannot be set. **Set it in the stream profile (`/usr/bin/env RESV_AUDIO_LANG=fra /data/reservoarr/reservoarr.py {streamUrl} {userAgent}`), not as a container variable:** a container variable never reaches the script, see [Where settings go](#where-settings-go). Empty leaves the command exactly as before. |
| `RESV_FFMPEG_STATS` | `0` | `1` adds `-stats`, so ffmpeg's `frame=… speed=…` line reaches Dispatcharr and its buffering failover can move a starving feed to the next stream. `-loglevel warning` is unchanged (invariant #9), and the progress line goes to stderr only, never to `delaybuf.log`. |

## When to bump what

- **Cushion too small for your CDN's prime-time gaps** → raise `RESV_TARGET_S` (cushion target) and `RESV_MAX_BYTES` (RAM cap) together. Each +10s of cushion is ~6–8 MB of extra RAM at typical HD bitrates. At the default `RESV_FLOOR=1.0` a higher target keeps more of what the CDN front-loads and nothing more: if `cushion=` already sits under the target, raising it changes nothing on its own.
- **Cushion stays well under the target, on Plex** → `RESV_FLOOR=0.97` builds the rest by feeding Plex ~3% under realtime until the target is reached. Watch for stutters: that deficit is taken from the client's buffer.
- **Micro-stutters every so often while the log looks healthy** → update to 6.6.0 or later: earlier releases fed a channel whose bitrate varies below realtime whenever it ran denser than its 90s average, which no setting changes. Then check `out` against `crate` over several minutes: 3–5% under means the player is fed below realtime to bank cushion: remove `RESV_FLOOR`, or on a release before 6.5.0 add `RESV_GRACE_S=inf`.
- **Stall watchdog firing on benign gaps** → raise `RESV_STALL_S`. The default 25s sits above the CDN's normal burst-gap; if yours is longer, set it slightly above your observed worst-case.
- **Arming the #5 detector** → see the arming-test recipe in the [CHANGELOG](../CHANGELOG.md) v6.1.0 entry. Don't flip `RESV_TS_RECONNECT=1` blindly; it's gated on evidence that fresh-edge reconnects actually serve clean content for your provider.
